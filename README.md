# LeetCode Lab

Practice LeetCode problems in Python with real tests, inside one small
container. No ports, no services, and it works offline once built.

The problems, tests and helpers are generated by
[leetcode-py](https://github.com/wislertt/leetcode-py); this repo packages it
as a ready-to-use dev container. See [Credits](#credits).

## Setup

You need **Docker Desktop** and **VS Code** installed.

1. **Start Docker Desktop** and wait until it says it's running (whale icon
   in the taskbar/menu bar stops animating).

2. **Install the Dev Containers extension** in VS Code: open the Extensions
   view (`Ctrl+Shift+X`, or `Cmd+Shift+X` on Mac), search **Dev Containers**,
   and install the one by Microsoft.

3. **Get the code** into a normal folder, *not* inside OneDrive, iCloud or
   Dropbox:

   ```bash
   git clone https://github.com/ethanluchs/leetcode-lab.git
   ```

   No git? On the GitHub page click **Code → Download ZIP** and unzip it.

4. **Open the `leetcode-lab` folder in VS Code** (**File → Open Folder…**).

5. **Reopen in Container.** Click **Reopen in Container** in the pop-up at the
   bottom right. If you missed it, press `F1`, type
   `Dev Containers: Reopen in Container`, and press Enter.

   The first time takes a minute or two while the container builds.

6. **Check it works.** Open a terminal in VS Code (**Terminal → New
   Terminal**). It opens *inside* the container. Run:

   ```bash
   cd leetcode/two_sum
   pytest -q
   ```

   You should see `15 failed`. That's correct: you haven't solved it yet.

You're set up. Next time, just open the folder in VS Code and it reconnects
to the container automatically.

### Terminal only (no VS Code)

```bash
docker compose build          # ~1 min, once
docker compose run --rm lab   # opens a shell in the container
```

You're now in `/work`, which is the same folder as `./work` on your machine.
Edit files in any editor and run tests in the container. `exit` leaves; your
work stays in `./work`.

## Tutorial

Every command below runs in a terminal **inside the container** (in VS Code,
**Terminal → New Terminal** after reopening in the container). The prompt
shows `student@...:/work`. If it doesn't, you're on your own machine and the
tests won't run properly.

### 1. Pick a problem and read it

```bash
ls leetcode                  # the problems you have
cd leetcode/two_sum
```

Each problem folder contains:

| File | What it's for |
| --- | --- |
| `README.md` | the problem statement, difficulty and topics |
| `solution.py` | **your code goes here** |
| `test_solution.py` | the test cases |
| `helpers.py` | runs your solution and checks the answer (used by the tests) |
| `__init__.py` | lets pytest import the folder; ignore it |

Open `README.md` in VS Code and right-click → **Open Preview** to read it
nicely formatted, or run `cat README.md`.

### 2. Run the tests

```bash
pytest -q
```

Each `.` is a passing case and each `F` a failing one, with a summary at the
end like `15 failed`. You haven't written anything yet, so that's expected.

A few cases may pass before you've written any code, because an empty answer
happens to be correct for some inputs. Only all-green counts.

### 3. Write your solution

Open `solution.py`. You'll find the function already set up with a `TODO`:

```python
class Solution:
    # Time: O(?)
    # Space: O(?)
    def two_sum(self, nums: list[int], target: int) -> list[int]:
        # TODO: Implement two_sum
        return []
```

Replace `return []` with your solution, save, and run `pytest -q` again.
Repeat until you see only passes, e.g. `15 passed`. Filling in the
`Time`/`Space` comments is good practice for interviews.

### 4. Zero in on failures

```bash
pytest -x              # stop at the first failing case
pytest -v              # list every case by name, PASSED or FAILED
pytest --lf            # re-run only the cases that failed last time
pytest -k nums3        # run only cases whose name contains "nums3"
```

Case names come from their position in the test list, counting from 0. For
example `test_two_sum[nums3-10-expected3]` is the **4th** case.

### 5. See what went wrong

A failure only says `AssertionError`; it doesn't show your answer. To see
more, run with `-s`, which shows each case's inputs and anything you
`print()`:

```bash
pytest -s -k nums3
```

```
... | DEBUG | ... - Running test_two_sum(nums=[2, 5, 5, 11], target=10, expected=[1, 2])
```

Add `print(...)` lines inside your solution to inspect values, and remove
them when you're done.

### 6. Add your own test cases

Think of an edge case the tests miss? Add it. In `test_solution.py`, every
line in the list under `@pytest.mark.parametrize` is one test case. The
values appear in the same order as the names on the line above:

```python
    @pytest.mark.parametrize(
        "nums, target, expected",
        [
            ([2, 7, 11, 15], 9, [0, 1]),
            # ...
            ([0, 1], 1, [0, 1]),
            ([4, 6, 1], 7, [1, 2]),      # <- your new case
        ],
    )
```

Run `pytest -q` and your case is included. Make sure your expected answer is
actually right: a wrong expected value fails even when your code is correct.

**Add cases freely, but never change or delete the existing ones to make
them pass.** They're the contract, and they include the LeetCode examples
plus edge cases.

Trees and linked lists are written as lists, the same way LeetCode writes
them: level by level, with `None` for a missing child. In
`invert_binary_tree`, a case looks like this:

```python
            ([4, 2, 7, 1, 3, 6, 9], [4, 7, 2, 9, 6, 3, 1]),
#             input tree             expected tree
```

To see what a list looks like as a tree, try this in `python`:

```python
from leetcode_py import TreeNode, ListNode

print(TreeNode.from_list([3, 9, 20, None, None, 15, 7]))
# 3
# ├── 9
# └── 20
#     ├── 15
#     └── 7

print(ListNode.from_list([1, 2, 3]))
# 1 -> 2 -> 3
```

### 7. Run everything

From `/work` (`cd /work`), `pytest -q` runs every case of every problem. To
run one problem from there, give its folder: `pytest -q leetcode/two_sum`.

### 8. Start a problem over

The container keeps a clean copy of every problem. To reset one solution:

```bash
cp /opt/seed/leetcode/two_sum/solution.py /work/leetcode/two_sum/
```

### 9. Get more problems

```bash
lcpy list                                  # browse all available problems
lcpy gen -n 15 -o /work/leetcode           # add problem #15 (3Sum)
lcpy gen -s valid_anagram -o /work/leetcode  # or add one by name
```

This works offline and takes a few seconds. Problem folders are named after
the problem, not its number: problem 15 appears as `leetcode/three_sum`.

Your work lives in `./work` on your own computer, so it's safe even if the
container is deleted or rebuilt.

### Smoke test before the session

```bash
docker compose build
docker compose run --rm lab bash -c '
  lcpy --help >/dev/null && echo "lcpy OK" &&
  python -c "import pytest; print(\"pytest\", pytest.__version__)" &&
  ls leetcode &&
  cd leetcode/two_sum && pytest -q 2>&1 | tail -n 1'
```

Expect `15 failed`, because the stubs are unimplemented. Run
`docker compose run --rm lab true` twice: the first run prints
"First run -- seeding", the second prints nothing.

Expected noise: the build prints `Found 11 errors (11 fixed, 0 remaining)`.
That's ruff auto-formatting the generated files, not a failure.
`devcontainer up` prints `Error fetching image details: No manifest found`,
which is also harmless.

### Linux

The container runs as uid 1000, which is the first user on almost every Linux
laptop, so most Linux students need nothing extra. macOS and Windows (Docker
Desktop) never need anything extra.

If a Linux student's `id -u` isn't 1000 (shared or university-managed
machines), the first run fails with
`cp: cannot create directory '/work/leetcode': Permission denied`.
Run as their own uid instead:

```bash
docker compose run --rm --user "$(id -u):$(id -g)" lab
```

The prompt then shows `I have no name!`, which is cosmetic; tests and edits
work normally.

`work/` is committed (via `work/.gitkeep`) on purpose. If it's missing, Docker
creates it owned by root and the first run fails with the same error even
for uid 1000. Fix: `sudo rm -rf work && mkdir work`.

Tested with Docker Desktop's WSL2 integration (Ubuntu 24.04), which passes
uids through like native Docker Engine. Not tested on a native Linux install.

### Picking the problem set

Default: Two Sum (1), Valid Parentheses (20), Best Time to Buy and Sell Stock
(121), Valid Palindrome (125), Invert Binary Tree (226).

Change it with the `GEN_ARGS` build arg in `compose.yaml`:
`-t grind-75` (75 problems), `-t blind-75` (75), `-t neetcode-150` (150),
`-d Easy`, `-s two_sum`, or `--all`. The package bundles 1,404 problems.
